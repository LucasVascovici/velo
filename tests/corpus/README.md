# Golden corpus

Small repositories and bundles written by **tagged release builds**, with
expectations read straight from the databases those builds wrote. A test that
opens them with the current build proves we can still read what was shipped.

**A change that alters a golden file's expected output is a format change and needs a FORMAT.md entry and a changelog line under the format heading.**

Golden files are only ever regenerated by rebuilding the tagged release, never
by a newer build. `.gitattributes` marks `tests/corpus/**` as `-text` so no
line-ending conversion touches golden bytes. Never run `velo` against the
checked-in copies (even `fsck` opens the database); work on a copy.

## Contents

| Tag | Repository format (`user_version`) | Bundle wire | Repo | Bundle |
|---|---|---|---|---|
| v4.0.0 | 2 | v3 | `repos/v4.0.0/` | `bundles/v4.0.0.v3.bundle` |
| v5.0.0 | 3 | v3 | `repos/v5.0.0/` | `bundles/v5.0.0.v3.bundle` |
| v5.1.0 | 3 | v3 | `repos/v5.1.0/` | `bundles/v5.1.0.v3.bundle` |
| v5.1.2 | 3 | v3 | `repos/v5.1.2/` | `bundles/v5.1.2.v3.bundle` |

Expectations for each are in `expected/<tag>.json`: `user_version`,
`snapshots`, `file_map` per snapshot, `tags`, `snapshot_meta`, `renames`,
`trash_ids`, `stash_names`, `branch_tips`. Branch tips are empty strings in
every golden: those releases did not record tips in the `branches` table, so
the tip is the newest snapshot of the branch.

Every golden holds: branches `main` and `feature`, a clean merge snapshot, a
rename edge (`src/a.txt` to `src/renamed.txt`, via `velo mv`), an author (the
reserved `velo` metadata namespace, from `VELO_AUTHOR_NAME`/`VELO_AUTHOR_EMAIL`),
the tag `v1`, a stash named `wip`, an undone snapshot in the trash, a CRLF
file, a binary file and a nested directory.

Differences by tag:

- **v4.0.0** ships no `velo-mcp`, so it has only the reserved-namespace
  metadata (the author) and no app-namespace metadata.
- **v5.0.0, v5.1.0, v5.1.2** also carry app metadata written through
  `velo-mcp`: `corpus.step = meta`, plus the `mcp` namespace rows the server
  adds.

No release ever wrote a bundle v2. `bundles/synth.v2.bundle` is synthesized:
take a v3 bundle of a history with no renames, set the `u32` version at byte
offset 8 to 2, and drop the trailing renames count (`u32 0`). The layout is
docs/FORMAT.md section 9. It was made from the v4.0.0 build.

## Signed bundles (wire v4)

`bundles/signed.v4.bundle`, `bundles/bad-signature.v4.bundle` and
`bundles/unknown-algorithm.v4.bundle` are **not** from a tagged release: no
release has written wire v4 yet. They were written by the 5.2.0 development
build (the ignored `write_the_v4_goldens` test in
`crates/velo-core/tests/corpus.rs`, run with `VELO_CORPUS_WRITE=1`, with fixed
timestamps so the ids are stable). They are pinned from now on under the same
golden-change rule as everything above; never regenerate them.

- `signed.v4.bundle`: two snapshots on `main`, both signed by the test key.
- `bad-signature.v4.bundle`: the same, with the last hex digit of one
  signature flipped. Applying it fails with `UntrustedData` and imports nothing.
- `unknown-algorithm.v4.bundle`: the same history, one row with algorithm
  `test-algo`. It applies; `verify` reports the row as unverifiable.

`keys/test.seed` is the signing seed for these bundles. It is a **test-only
key, never trust it**: it is public, and anyone can sign with it.
Expectations (ids, signer public key, rows) are in `expected/bundles.v4.json`.

## Regenerating

Build the tagged release in a scratch worktree (never commit worktrees or
binaries), then run the script with that build's binaries:

```sh
git worktree add /tmp/velo-v5.1.2 v5.1.2
(cd /tmp/velo-v5.1.2 && cargo build --release -p velo-cli -p velo-mcp)   # v4.0.0: -p velo-cli only
python tests/corpus/generate.py \
    --velo /tmp/velo-v5.1.2/target/release/velo \
    --mcp  /tmp/velo-v5.1.2/target/release/velo-mcp \
    --tag v5.1.2 --out tests/corpus
git worktree remove --force /tmp/velo-v5.1.2
```

For v4.0.0 omit `--mcp`, and add `--synth-v2` to rewrite
`bundles/synth.v2.bundle`. The script needs Python 3 and the standard library
only. Timestamps and hashes differ on every run, so regenerating changes every
golden file; that is why it is done only when a new format step is released.

## Spec-written v4 fixture

`repos/format-v4/` and `expected/format-v4.json` are **not** from a tagged
release. They are produced only by `write_format_v4.py`, a standard-library
Python script written from docs/FORMAT.md alone (objects, the section 4.2
identity recipe, the schema, signatures, and the v4 storage section). It shares
no code with velo, so a mistake or an ambiguity in the spec shows up here rather
than being baked into the Rust writer. The history uses K = 4 so keyframes and
chains of depth 0 to 3 appear in about a dozen snapshots, and includes a merge
delta, deletes, a mode change, a rename edge, two chained trashed snapshots, a
tag and a signature (key: `keys/test.seed`). The expectations add
`tree_deltas`, `tree_delta_rows`, `keyframes`, `k` and an `ops` list that a
test can replay with the real engine.

It is never regenerated by a velo build, and it is pinned under the same
golden-change rule as everything above. Re-running the script
(`python tests/corpus/write_format_v4.py --out tests/corpus`) must reproduce the
checked-in bytes. The v3 corpus test skips `format-*` expectations because this
build would refuse the repository with `SchemaTooNew`.

## Old-release check

`old_release_check.py --old <velo 5.x> --new <velo 6.x>` (CI job `old-release`,
which builds `v5.3.0`, or `v5.2.0` if that tag does not exist yet) asserts that

1. the old binary refuses a copy of `repos/format-v4` with a non-zero exit and a
   message naming format v4 and the version it supports (it prints a finding
   when the message gives no upgrade advice; a released binary cannot be changed);
2. a repository built by the new binary (delta chains, a merge, tags, a
   signature) bundled with `bundle create` and applied by the old binary into a
   fresh repository has the same snapshot ids, branches, and file contents at
   every branch tip and tag.

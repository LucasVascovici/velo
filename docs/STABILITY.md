# Stability

What an adopter of velo is promised, and which CI job or test makes each
promise checkable instead of aspirational.

## Stable

| Promise | Enforced by |
|---|---|
| The `velo-core` and `velo-merge` public API follows semver. | The `semver` CI job runs `cargo-semver-checks` against the previous release tag. One known exception, `Bundle.signatures`, is described under "Not stable". |
| The repository format: a build refuses a repository written by a newer format, migrates older ones forward only, and [FORMAT.md](FORMAT.md) is normative. | The `corpus` CI job and `tests/corpus/`. |
| Bundle wire versions 2, 3 and 4 are read forever. | The `corpus` job: `tests/corpus/bundles/` holds a v2 bundle, v3 bundles written by v4.0.0, v5.0.0, v5.1.0 and v5.1.2, and signed, bad-signature and unknown-algorithm v4 bundles. |
| Exit codes (see the [Exit codes table](../README.md#exit-codes)). | The CLI black-box tests in `crates/velo-cli/tests/cli.rs`. |

The golden repositories cover formats 2 and 3 (`repos/v4.0.0`, `v5.0.0`,
`v5.1.0`, `v5.1.2`). Each is opened by the current build, its contents compared
with an expectation read from the database the released build wrote, and
migrated or refused as FORMAT.md says. Goldens are written only by the tagged
release that defines them, never regenerated by a newer build.

## Not stable

- **CLI output text.** Wording, column layout and hints can change in any
  release. Script against exit codes, or against the embedder API, not against
  text.
- **`#[doc(hidden)]` items** such as `Error::samples`, the `failpoint` and
  `fuzzing` modules and the `Bundle.signatures` field, and the `failpoints` and
  `fuzzing` Cargo features, and the `timing` module and feature. They exist for
  tests, fuzzers and profiling, and may change or
  vanish in any release. `cargo-semver-checks` does not honour `#[doc(hidden)]`
  on a field of a constructible struct, so it reports `Bundle.signatures`
  (added in 5.2.0) as `constructible_struct_adds_field`. That finding is a
  known, accepted exception: do not construct `Bundle` with a struct literal;
  obtain one from the bundle create and read functions in `commands::bundle`.
  Whether to keep this exception or make `Bundle` `#[non_exhaustive]` in 6.0 is
  open. Until that is settled the `semver` job allows the
  `constructible_struct_adds_field` lint for `velo-core`
  (`[package.metadata.cargo-semver-checks.lints]` in its `Cargo.toml`), which
  also hides the same kind of break on any other struct; review new public
  fields by hand.
- **`velo-ffi`, `velo-mcp` and the Python, Node and WASM bindings.** They are
  0.x and not published to a registry. Their surface may change between any two
  commits; pin a commit if you depend on them. They follow the core's stable
  API, so what they wrap does not break under them.

## Deprecation policy

An API slated for removal is marked `#[deprecated(note = "use <replacement>")]`
for at least one minor release before it is removed in the next major release.
The `semver` job catches a removal that skipped this.

## MSRV policy

`rust-version` in the workspace `Cargo.toml` is derived from the dependency
tree, not chosen, and the `msrv` CI job builds with exactly that toolchain.
Raising it is allowed in a minor release and is announced in the changelog.

## How a format change is announced

1. An entry in [FORMAT.md](FORMAT.md).
2. A changelog line under a format heading.
3. The golden-change rule from `tests/corpus/README.md`:

   > A change that alters a golden file's expected output is a format change and
   > needs a FORMAT.md entry and a changelog line under the format heading.

The `corpus` job fails when a golden's expected output changes, so a format
change cannot land unannounced.

6.0.0 is the format-v4 release. A repository-format change is not a Rust API
break, but any Rust API break in 6.0 is listed here as an exemption, as
`Bundle.signatures` was.

## Appendix: the `#[non_exhaustive]` audit

Public enums and option or result structs should be `#[non_exhaustive]` so a
field or variant can be added without a major release. Adding the attribute to a
type that already shipped is itself a breaking change, so the types below, all
from before 5.2.0, stay as they are and are **planned for 6.0**.

Every public type new in 5.2.0 (`Limits`, `Limit`, `PathProblem`, the
`serve::http` types, the `sign` types, `Synced`, `SyncOptions`, `SignatureRow`
and the rest) carries `#[non_exhaustive]`; this was checked by diffing against
`v5.1.2`.
